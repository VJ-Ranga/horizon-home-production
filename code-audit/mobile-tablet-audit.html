01 · Executive summary

Mobile is not one animation rule

The project has one shared logical frame timeline, but phone and tablet use different assets and responsive layouts. Compact input is controlled at the source pace of 5.1922fps: normal sections use frame-distance transitions, while scroll-through and carousel sections consume direct touch/wheel input without an automatic post-release glide. The remaining risks come from section contracts being mixed together: short frame windows, pinned holds, carousels, scroll-through content, inner readers, frame limiting, and browser gesture arbitration.

Accepted mobile tradeoff

Intentional

The compact 5.1922fps pace, bounded frame loading, and mobile asset strategy are intentional performance and bundle-size decisions. They are accepted for this delivery and are not treated as defects.

DecisionKeep the current frame rate, quality, and asset-size strategy. Do not redesign this path to chase desktop-level fidelity on compact devices.

Most important distinction

Shared vs separate

Section frame numbers and timing data are shared. Frame assets, intro videos, carve geometry, layout density, and phone/tablet card geometry are separate.

Desktop scope

Frozen

Desktop Lenis, desktop timing overrides, desktop assets, and desktop visual behavior are not part of the remediation work unless the client requests it.

04 · Scroll ownership

Why scrolling is not fully native today

Desktop reference path

Desktop creates Lenis during the scroll phase. Lenis smooths wheel input, the frame driver advances it, then the driver samples page position and emits one canonical frame/scroll value.

desktop wheel -> Lenis -> frame driver -> timeline -> layers + canvas

Phone/tablet current path

Compact does not create Lenis. The coordinator listens at the window, checks reader edges, prevents outer wheel/touch momentum, and uses two paths: normal sections animate to the adjacent frame at 5.1922fps; scroll-through and carousel sections apply capped movement directly from each touch/wheel input.

touch/wheel -> compact controller -> normal timed path OR direct special input -> frame driver

Why it can still drift

The compact frame guard limits the emitted frame to two frames per driver tick, while the controlled document position is updated separately. The direct-input cap reduces the gap, but real-device testing is still required to confirm that painted frame, document position, and section state remain aligned.

Why a section can disappear

Short enter/exit windows can be crossed before the layer has enough readable dwell. Pinned sections solve this with virtual budgets, but only if the controller recognizes the budget and the layer stays visible until the panel finishes.

Why readers are different

Inner readers need native overflow scrolling. They should consume the gesture while they have room, then release the outer page only at the top or bottom edge.

What should remain one owner

Each mode should have one outer scroll owner, one frame scheduler, and one section-specific transform owner. Avoid adding another Lenis, rAF, CSS transition, or scroll listener to solve one section.

Short windows are easy to outrun

Medium

Symptom: governance and bridge sections appear briefly or disappear before content can be read.

Cause: a 20-40 frame visual window can be smaller than one high-velocity touch flick.

Best practiceUse explicit compact hold budgets for readable sections. Do not solve this by globally slowing every section.
timeline.ts · sectionLayerStateAt()

Special content has different geometry

Medium

Symptom: carousels or long panels feel too fast, stop short, or fade before the last card/content.

Cause: carousel and scroll-through sections are not ordinary frame windows; they need raw scroll budgets and their own completion checks.

Best practiceKeep carousel and scroll-through budgets explicit and test their start, middle, end, and reverse paths separately.

Accepted

Real-device evidence is missing

Open

Symptom: desktop emulation can hide synchronization, decode, or content-completion issues on iOS Safari or Android Chrome.

Cause: toolbar resizing, touch arbitration, bitmap decode pressure, and browser memory behavior are not reproduced by a desktop viewport.

Best practiceRecord actual gesture duration, frames painted, dropped frames, scroll owner, and active section around the final frame-rate contract. Do not change the global timing based on this validation.

08 · Best-practice plan

Recommended order of work

1 · Implemented

Use one compact input owner

Normal sections use source-speed transitions. Scroll-through and carousel sections use direct capped touch/wheel input without an automatic post-release animation. Keep one frame scheduler and one section transform owner.

2 · Validate

Measure special sections

Test Sections 08, 12, 14, 16, 17, and 18 independently. Record input duration, document position, emitted frame, painted frame, and active section. A generic global slowdown is no longer the target.

3 · Measure

Separate phone from tablet only with evidence

Start with shared compact timing. Add phone-specific or tablet-specific dwell only when real device measurements show a meaningful difference in decode, content height, or touch behavior.

4 · Protect

Freeze desktop

Do not change desktop timeline, Lenis, desktop assets, or desktop layout while mobile/tablet remediation is underway. Keep separate commits and verify desktop remains untouched.

Audit boundary: This report documents the mobile/tablet problem and recommended fixes. It does not claim real-device validation has passed, and it does not authorize desktop changes.
