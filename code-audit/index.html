04 · Responsive architecture

One UI system, specialized assets

The current mobile/desktop strategy is correct for this type of animation-heavy experience. Separate entire component files only when markup and interaction are genuinely different.

Shared React components

Semantic sections, shared content, shared timeline rules, and common controls keep behavior consistent.

+

Responsive specialization

Media queries, mobile frame assets, touch handling, frame-rate limiting, and mobile scroll-through behavior adapt the experience.

Desktop

  • Full viewport composition.
  • Higher-resolution frame sets.
  • More decoded frames retained.
  • Mouse and smooth-scroll interactions.

Tablet

  • Dedicated 701-1100px behavior.
  • Inner scrolling only where needed.
  • Reduced composition density.
  • Responsive media sizing.

Phone

  • Portrait 360x640 frame assets.
  • Sliding decode window.
  • Touch-native scrolling and frame guard.
  • Reduced-motion fallback.
Suggestion · Desktop

Protect the full-quality path

Keep desktop on the existing full-load route for the smoothest hover and wheel experience. Measure decode time, memory, and frame pacing before adding a desktop cache or lowering quality.

Suggestion · Tablet

Prioritize the wider window

Use the tablet loader independently from the phone loader: retain a wider frame window and moderate concurrency for landscape and larger screens, then re-evaluate after rotation or viewport changes.

Suggestion · Phone

Keep memory bounded

Keep the phone loader on portrait assets, lower concurrency, a smaller sliding decode window, and last-painted fallback. Pause only at declared settled frames, never at arbitrary in-between frames.

05 · Smooth scroll and animation diagnosis

Why the experience can feel glitchy

The symptoms are not just an easing problem. The Community carousel has a confirmed feedback mismatch between CSS transition timing, frame-driven transforms, layout measurement, scroll smoothing, and frame decoding. Fix the ownership boundaries before tuning more delays.

Community carousel has two transform clocks

Critical

Confirmed: CommunityLayer writes a new translate3d value from the frame driver while CSS also animates that same transform for 140ms. Every new scroll tick restarts the transition, so the rail is always chasing an old target and can trail, snap, or continue moving after scrolling pauses.

CommunityLayer.tsx:104-146 · lab.css:5347-5354
Fix strategyUse one owner for interpolation. Either write the rail position directly from one scheduler or implement the easing in that scheduler; do not combine per-frame JavaScript updates with a CSS transform transition.

Carousel measures layout during every animation update

High

Confirmed: each desktop update calls getComputedStyle, reads card width, rail width, and viewport width, then writes the rail transform. These reads can force layout immediately after other animation writes and produce uneven frame pacing on slower devices.

CommunityLayer.tsx:108-145
Fix strategyCache card and viewport geometry on mount and resize. Keep the frame callback to pure math plus one transform write, and recalculate only when the carousel geometry actually changes.

Lenis and the frame driver run separate rAF clocks

High

Confirmed: Lenis has its own loop while the shared frame driver has another. Depending on callback order, the frame calculation can consume the previous Lenis position for one tick while the carousel and canvas respond to different samples.

AnimationLab.tsx:455-479 · useFrameTimeline.ts:143-206
Fix strategyMake one scheduler advance Lenis and emit the canonical scroll/frame sample, or explicitly define and test the ordering so every visual layer consumes the same value.

Frame decode fallback can look like a visual jump

Medium

Confirmed: when the requested frame is not decoded, the scrubber selects the nearest loaded frame. During a fast gesture this can move backward or forward unpredictably, while the requested background position continues to advance.

LabScrubber.tsx:364-417
Fix strategyPrefer the last painted frame until the requested frame is ready, expose decode lag in diagnostics, and avoid choosing a future frame that makes the footage appear to jump.

Mobile reader gesture handoff improved

Fixed

Glance and Financial now claim the first touch before the page timeline advances, then release Lenis prevention at the reader's top or bottom edge. Mobile scroll-through panels also land directly on the latest frame sample instead of stopping short.

GlanceLayer.tsx · FinancialLayer.tsx · LeadershipLayer.tsx · StrategyLayer.tsx
Still requiredValidate on real iOS Safari and Android Chrome. Desktop emulation cannot reproduce touch arbitration, browser toolbar resizing, or mobile bitmap memory pressure.

Multiple scroll paths are intentional, but tightly coupled

Warning

Why it exists: Lenis smooths desktop wheel input, native touch scrolling is deliberately kept on phones, inner panels allow long content to be read, and programmatic scroll is required for the infinite loop transition.

Actual risk: these are not independent animation systems, but they can all read or write related scroll state. Direct window.scrollTo, document scroll assignments, Lenis scrollTo, nested overflow areas, and section rAF effects can race during a loop, resize, or gesture.

AnimationLab.tsx:451-479, 581-613 · LeadershipLayer.tsx:165-186 · globals.css:193-200
Keep the reason, fix the boundaryKeep one page-scroll owner per mode: Lenis for desktop wheel smoothing, native scroll for touch, and a guarded loop controller for programmatic jumps. Sections should consume one canonical progress value and never rewrite page scroll themselves.

Frame driver and scroll can drift

Critical

Symptom: text arrives before the background, sections appear to skip, or a fast flick shows the wrong frame.

Likely root cause: the scroll position changes faster than the required frame window can decode, while animation layers respond immediately.

AnimationLab.tsx:650-742 · LabScrubber.tsx:146-155
Fix strategyUse one canonical frame value, gate only the small required decode window, and render a stable previous frame while the next frame is unavailable. Never block the entire page on the full 1,125-frame set.

requestAnimationFrame loops need clear ownership

Warning

Symptom: CPU spikes, movement continues after leaving a section, or mobile scrolling becomes warm and uneven.

Likely root cause: multiple rAF loops run in separate components and each writes styles or reads layout during the same frame.

LeadershipLayer.tsx:139-193 · AnimationLab.tsx:634-647
Fix strategyOne scheduler should read scroll/frame state once per tick. Batch DOM writes after reads, cancel every rAF on cleanup, and run section-specific work only while the section is active.

Responsive rules can disagree

Warning

Symptom: a layout works on desktop, breaks on mobile, or changes after rotation and browser toolbar collapse.

Likely root cause: CSS uses many overlapping breakpoints while JavaScript uses separate 700px and 1100px matchMedia decisions. Dynamic viewport height also changes on mobile.

lab.css:250-312, 1095-1126, 4968-4999 · frameDirMobile.ts:56-64
Fix strategyDefine breakpoint tokens once, use the same breakpoint contract in CSS and JavaScript, prefer dvh/svh intentionally, and test resize/orientation transitions rather than assuming one mount-time value.

Inner overflow can trap gestures

Warning

Symptom: the page stops responding at the edge of a card panel, or a user cannot tell whether they are scrolling a panel or the page.

Likely root cause: multiple nested scroll areas use overflow-y: auto and touch momentum; each has different overscroll behavior.

globals.css:184-200, 273-281 · lab.css:4968-4970
Fix strategyUse inner scrolling only for content that cannot fit. Add visible scroll affordances, keep overscroll-behavior consistent, and use a single continuous scroll-through pattern for long mobile sections.

Hydration-safe viewport logic costs an extra render

Warning

Symptom: a flash of the wrong frame source or a brief layout shift after the page becomes interactive.

Likely root cause: browser-only viewport detection is intentionally delayed, but the mounted state creates a second render and can briefly disagree with CSS.

LabScrubber.tsx:118-129 · LabIntro.tsx:74-100
Fix strategyKeep SSR output stable, but isolate browser-only asset selection in one hook. Add a poster fallback and do not start desktop loading before the phone decision is known.

Safe debugging sequence

  1. Record the exact device, viewport, browser, scroll gesture, section, and frame where the glitch begins.
  2. Log one canonical scroll value, one frame value, decode status, and active section per animation tick.
  3. Temporarily disable Lenis, then inner scrollers, then visual layers to identify the first failing boundary.
  4. Form one hypothesis and make one minimal change. Do not adjust easing, cache size, and breakpoints together.
  5. Verify the same gesture on desktop, tablet, phone, rotation, reduced motion, and slow network.

06 · File structure and coding method

Current versus optimized structure

The current structure is understandable, but the animation coordinator is doing too much. The recommended structure keeps timing, assets, layout, and content separate so a mobile change cannot silently damage desktop behavior.

Current structure

src/
  app/
    page.tsx
    animation-lab/page.tsx
    globals.css
  components/
    AnimationLab/
      AnimationLab.tsx       # coordinator, scroll, loop, loading gate
      LabScrubber.tsx         # frame loading, cache, canvas paint
      timeline.ts             # sections and frame calculations
      *Layer.tsx              # section UI and local effects
      lab.css                 # all lab layout and animation styles
    GlobalHeader.tsx
    BackgroundMusic.tsx
  styles/tokens/
tests/                        # not included in tsconfig or package script
public/frames*                # very large animation assets
public/vendor/                # minified third-party code

Risk: the structure is componentized, but shared responsibilities and the 5,929-line stylesheet make changes hard to isolate.

Recommended structure

src/
  app/
    ...
  features/animation-lab/
    AnimationLab.tsx          # composition only
    model/timeline.ts          # pure frame/section calculations
    model/types.ts             # shared contracts
    controllers/scroll.ts     # one scroll owner
    controllers/loop.ts       # programmatic loop transition
    controllers/frame-driver.ts # one rAF scheduler
    assets/frame-resolver.ts  # desktop/mobile density selection
    assets/frame-cache.ts     # bounded decode cache
    sections/*Layer.tsx       # presentational section components
    styles/base.css
    styles/sections/*.module.css
  shared/hooks/useViewport.ts
  shared/ui/Dialog.tsx
tests/
  unit/timeline.test.ts
  unit/frame-cache.test.ts
  integration/scroll-flow.test.ts

Benefit: each module has one owner, clear inputs/outputs, and a focused test surface.

Preferred coding and comment method

  • Pure calculations: keep timeline mapping, easing, breakpoint decisions, and frame ranges as pure functions with no DOM access.
  • One owner per side effect: one module owns scroll, one owns the animation clock, one owns frame decoding, and one owns each dialog.
  • Stable contracts: pass typed values such as { frame, progress, phase } into sections instead of allowing sections to read or mutate global scroll.
  • Refs for imperatives: use refs for DOM nodes and mutable animation state, never as render data and never to bypass state synchronization.
  • Comments explain why: document browser limitations, synchronization assumptions, memory trade-offs, and why a workaround must remain. Do not comment obvious assignments.
  • Small commits: separate lint fixes, scroll ownership changes, cache changes, responsive changes, and visual polish so regressions can be isolated.
  • Validation with each change: type-check, lint, focused tests, then the full device matrix before combining optimizations.

07 · Detailed practice review

Quality areas to strengthen

TypeScript and React

Strong base
  • strict: true, path aliases, ES module interoperability, and bundler resolution are configured.
  • React 19 and Next.js App Router patterns are used consistently.
  • Improve purity and hook dependency compliance until source lint passes.
  • tests is excluded from TypeScript compilation, so add a separate type-check path if tests grow.

Testing

Current tests are useful but partly source-regex based. They can break from formatting changes without proving runtime behavior.

Next: add a package script and behavioral tests for timeline utilities, frame resolution, dialog control, and interaction controllers.

CSS maintainability

Improved

lab.css is now a 21-line ordered entrypoint importing shared shell, layout, intro, and section-owned styles.

Next: remove duplicate declarations gradually and consolidate breakpoint tokens without changing the visual cascade.

Accessibility

ARIA labels, dialog labels, focusable controls, reduced motion, and decorative canvas hiding are generally good.

Next: expose global menu state with aria-expanded and aria-controls; verify focus trapping and restoration on dialogs.

Images and loading

Raw images are appropriate in some animation paths but trigger Next.js optimization warnings in normal content areas.

Next: use next/image for ordinary images and add explicit loading/error fallback states.

Breakpoints

The code uses 480, 560, 600, 620, 640, 700, 720, 780, 900, and 1100px rules.

Next: document the intentional tiers and standardize where two breakpoints solve the same problem.

09 · Practical decision guide

Stabilize first. Refactor only where it pays.

A perfect architecture is not required for a client delivery. Keep intentional behavior that users need, fix issues that cause visible breakage, and postpone expensive cleanup when it does not reduce current risk.

Minimum safe client-delivery scope

Do first
  1. Fix source lint errors without changing visual timing.
  2. Exclude vendor code from lint.
  3. Make one scroll mode active per device class.
  4. Fix the specific broken mobile section instead of redesigning every section.
  5. Keep the last painted frame while loading the next frame.
  6. Test the exact client devices and browsers before release.

Safe compromises under deadline

Acceptable
  • Keep the monolithic CSS temporarily if visual behavior is stable.
  • Keep raw animation images where Next image optimization is not suitable.
  • Keep separate desktop/tablet/phone branches when their interactions differ.
  • Use a feature flag or route-specific behavior for experimental scroll changes.
  • Document known limitations instead of hiding them with broad lint disables.

Do not use as shortcuts

Avoid
  • Do not add more arbitrary timeouts to hide frame or scroll races.
  • Do not disable all React lint rules or ignore the whole source directory.
  • Do not force one mobile layout to behave like desktop just to reduce files.
  • Do not preload every high-resolution frame on phones.
  • Do not change Lenis, frame pacing, breakpoints, and CSS overrides in one commit.
